# design-sync notes — Mason Connect Design System

## Fixes and known issues

- `[GENERAL]` **TrendLineChart's Line entrance animation is not stabilized by the compare harness.** recharts/react-smooth drives the Line's mount-draw animation via `requestAnimationFrame`, which Playwright's `animations: 'disabled'` screenshot option does not cover (it only fast-forwards CSS/WAAPI animations). Both the storybook reference and the ds preview get captured mid-animation, showing a partial line on both sides. Verified manually (opened the preview HTML directly, waited 2.5s past the default 1500ms `animationDuration`): the full, correct line renders, matching the story data exactly. Graded `close` with this note rather than `match`, since the captured pixels do show a visible partial-line delta — but there is no component-level defect and no fix applied (Task 17 of the build deliberately did not expose an `isAnimationActive` escape hatch on the shipped component, to keep production rendering fully animated). CategoryBarChart's `<Bar>` does not appear to have the same issue — recharts' bar entrance animation renders a complete `t=0` frame synchronously before any `requestAnimationFrame` work happens (confirmed during Task 17's implementation), so its bars should be structurally complete even if not yet animated to their final "grown" height. Re-verify this on future syncs if the chart implementation ever changes.
- `[FONT_MISSING]` — validate warns that `"Calibri"` (`--mc-font-deck`) is referenced by `tokens.css` but no `@font-face` ships it. This is the "deck" (dark presentation theme) font — the deck theme is explicitly out of scope for v1 (see the design spec §3, §10) and no shipped component consumes `--mc-font-deck`. Accepted as-is; no `cfg.extraFonts` needed unless the deck theme is built in a future v2.
- `[FONT_MISSING]` — as of the 2026-08-31 re-sync, validate also warns about `"IBM Plex Sans"` (`--mc-font-tabular`). Same shape of finding, same acceptance: the `.mc-num` CSS class references the token, but no component's `className` actually applies `.mc-num` yet — it's meant for numeric text in a *consuming app* (KPI/monetary/date/percentage values), and no DS component internally uses it either. Font-loading is correctly left to the consuming app (`app/` self-hosts `@fontsource/ibm-plex-sans`). **Known follow-up, not fixed in this sync** (ruled non-load-bearing during the app build's final review, 2026-08-31): `.mc-num` itself doesn't yet set `font-family: var(--mc-font-tabular)` — it only sets `font-variant-numeric`/`font-feature-settings`, so today it's a no-op typographically even where applied. Wiring `.mc-num`'s `font-family` + applying it inside `Stat`/`ProgressBar`/chart-axis tick renderers is a deferred design-system PR (see the app repo's SDD ledger for that plan — bundled with the `ProgressBar` denominator-string gap found in the same review).
- **`text-finance-positive`/`text-finance-negative` weren't in the compiled CSS until this re-sync fixed it.** Root cause: these two Tailwind utilities (added alongside the `.mc-num`/finance tokens work) are meant for a *consuming app's* free-form text (a ledger/extrato row), never used inside any DS component itself — so Tailwind's `content` scan of `design-system/src/**` never saw the class strings and never emitted them into `dist/styles.css`, even though the underlying CSS custom properties (`--mc-finance-positive`/`--mc-finance-negative`) were present via `tokens.css`. Since `/design-sync` ships only the compiled `dist/styles.css`, the conventions header would have told the design agent to use two classes with no matching rule in the shipped bundle. Fixed by adding `safelist: ['text-finance-positive', 'text-finance-negative']` to `design-system/tailwind.config.ts` (commit `dd42ac1`). **General lesson for future token/class additions**: if a new utility class is meant for app-side use only (not applied inside any DS component), it needs an explicit safelist entry, or it silently never ships — check `dist/styles.css` for the literal class string, not just that the CSS custom property exists.
- **`Button`'s `fullWidth` prop (new story "Full Width") graded `match`** against its storybook render this re-sync — full-width solid button renders identically in both panels, no issues.
- **Card's `Unpadded` story shows no shadow in the storybook capture, but does in the ds capture** — capture framing, not a defect. Playwright's `el.screenshot()` on `#storybook-root` clips to the element's layout bounding box (via `getBoundingClientRect`, which excludes box-shadow paint outside the box); the ds preview capture is full-viewport and shows the shadow unclipped. `Card.tsx` applies `bg-surface rounded-lg shadow` unconditionally regardless of `padded` — confirmed in source. Graded `match`.
- **CategoryBarChart prints `[PORTAL?]`** — recharts' `<Tooltip>` renders a `position:absolute` wrapper div in the DOM even when not hovered/open, tripping the harness's portal heuristic. Not a genuine overlay-escape defect: `.render-check.json` reports `gridOverflow: null` for this component, and captures with no hover triggered show a clean, fully-contained chart. `cfg.overrides.CategoryBarChart.cardMode: "single"` was considered and NOT applied — no observed defect to justify it. Its `<Bar>` also renders structurally complete (not partial) on both sides, consistent with the `[GENERAL]` TrendLineChart note above.

## Re-sync risks

- **Zero owned previews** (`.design-sync/previews/` is empty) — every one of the 15 components' generated preview rendered faithfully against its storybook story on the first capture, no fixes needed. This means there is nothing hand-maintained to go stale; if a future sync suddenly needs an owned preview for a component that never had one, that's a real regression worth investigating, not routine.
- **TrendLineChart is the only `close` grade** (all others are `match`) — tied to the `[GENERAL]` react-smooth/animation-timing note above, not to component correctness. If recharts/react-smooth is ever upgraded, re-verify this note still applies (the animation-completion timing could change).
- **`ListRow` and `NavTab` have no dedicated stories** — they only render as composed children inside `List`'s and `BottomNav`'s stories, so they were never individually captured/graded as top-level entries (consistent with `27/27 stories paired` and `15/15 storybook components` — 15 storied, not 17 bundle exports). If dedicated stories are added for either in a future sync, expect them to appear as new top-level `added` components.
- **No composition/screen-level stories exist** — every story is a single isolated component, never a composed screen combining several (e.g. a full "Painel" dashboard using `Card`+`Stat`+`TrendLineChart` together). The design spec (§7) anticipated these as Storybook-only reference stories, but no build task ever created them. This doesn't affect any individual component's fidelity, but it means the synced project has no high-fidelity composition example for the design agent to learn from — worth adding before/after a future sync if composition fidelity becomes a concern.
- **Select's `Profile Picker` story sets `value` without `onChange`** — known, accepted (design-system build plan artifact). Produces a React "controlled input without onChange" console warning in the browser console only; the rendered visual output is correct and was graded `match`. Not a design-sync issue.
- This is a **re-adopted, non-empty project** (`Mason Connect Design System`, previously built directly by a claude.ai/design agent from the repo's own planning documents, not by a prior `/design-sync` run) — the upload's `deletes` list was hand-reviewed against `list_files`, not derived from a diff anchor, since no prior `_ds_sync.json` existed. See the upload summary for exactly what was removed.
- **2026-08-31 re-sync**: anchored (first sync's `_ds_sync.json` present), atomic path, only `Button` needed re-verification (its content changed: `fullWidth` prop + story) — everything else carried forward via the anchor. `conventions.md` was updated this run (finance-* classes, `.mc-num`, `Button.fullWidth` documented) — validate their claims again on the *next* re-sync too, since `.mc-num`'s `font-family` wiring is still pending (see the `[FONT_MISSING]` bullet above); once that follow-up design-system PR lands, re-verify the conventions text still matches (it currently describes the intended behavior, which is correct guidance for the design agent, but isn't the full CSS reality yet).
